## 需修复的问题

### P1：冒烟测试可假阳性，也不能证明“恰载 3/2 个”

`smoke_test.ps1:30-55` 只打印各模组日志是否刷新，从不把缺失或陈旧加入 `$fail`；`tdfc.log` 根本不在 `$logs` 中，MSW 也没有可用文件日志断言。`:60-75` 取第一个找到的 `ModLoader.sol`，只检查文件原始字节里是否**包含** `ok_<入口类>` 字符串，没有核验状态时间是否属于这次启动、错误键是否更新、对象是否来自目标 app id，也不检查禁用项是否没有加载。`$alive` 仅打印、不参与断言。即使本次没有任何模组加载，只要旧 `.sol` 留着成功键，脚本也能报 `SMOKE PASSED`；即使禁用项被加载，它也能报通过。`onModSwfLoaded` 写入的成功键与 `modLoaderStatus()` 都是持久键（补丁脚本 `:121-149`），启动时没有清空或会话编号，放大了这个问题。反过来，在 SharedObject flush 失败但模组实际正常时，脚本会报失败。README `:150` 已承认该通道可能失效，但 `:164-173` 仍把脚本作为快速验证办法。

建议：本次启动生成唯一 run id 或清除专用状态；断言每个应载项本轮成功、每个禁用项本轮未初始化、无本轮错误；日志刷新必须进失败条件；检查进程健康；不要用 SOL 原始字节包含测试代替解析和值的时间核对。若 SOL 不可靠，主断言应改用各模组明确的本轮日志标记。

### P1：Steam 更新后的“幂等恢复”检查过宽，可能留下旧调用并造成重复装载

`patch_game_swfs.ps1:278-282` 只要导出的任意位置包含 `loadModsFromManifest` 字串就直接跳过，既不验证通用调用点存在，也不验证七个旧调用已消失、方法/字段齐全、manifest 路径正确。`Transform-MainFe` 的旧调用移除用带**精确缩进和换行**的字符串（`:156-165`, `:234-245`）；变体格式的 `this.loadXxxMod();` 不会删除。后续重新导出验证仍只检查同样的精确字符串（`:306-308`），所以若游戏更新或其他补丁改变缩进，旧调用与新通用调用可能同时执行而不报错。脚本还不校验每个目标预期的 7/3/2 移除数。

当前已部署三份导出中，旧调用确实已移除；这是**下次重跑/游戏更新时**的风险。建议在“已打补丁”分支和新产物验证分支都解析 `onEnterFrameLoader` 的实际调用集合，确认恰有一个通用调用、没有旧调用，并按目标核对预期移除数；有不认识的调用或结构变化时拒绝部署。三目标分别处理（`:339-350`）还会在某目标失败后留下其他目标已部署的混合状态，应在运行摘要中明确指出，或先生成并验证全部产物再统一部署。

### P2：新检出仓库缺少 `work/` 时，补丁脚本尚未启动就会失败

`patch_game_swfs.ps1:41` 在参数默认值里使用 `Join-Path $PSScriptRoot '..\work' -Resolve`，但 `work/` 被 `.gitignore:2` 忽略；全新检出时目录不存在。PowerShell 对不存在的目标执行 `Join-Path -Resolve` 会报“Cannot find path”，因此来不及运行脚本 `:337` 的创建目录语句。当前机器已有该目录，所以没有影响这次部署。建议默认值只做路径拼接/正规化，把创建目录放在参数绑定之后；本次用不存在的同级路径验证了 `-Resolve` 的失败行为。

### P2：目标 SWF 或清单缺失时，恢复脚本仍可能以成功退出

`patch_game_swfs.ps1:267` 把缺失目标返回 `skip(missing)` 而不是失败；`:334-336` 对清单缺失只发警告；`:348-352` 只有 `$failed` 非空才以错误码退出。因此清单没放好、甚至其中一份目标没找到，脚本也可能打印 `done.`，让自动恢复链误判为成功。建议对显式目标及清单缺失直接失败；可选目标应有单独的明确选项。

### P2：一行清单若触发同步异常，会阻止其后的所有模块发起加载

`patch_game_swfs.ps1:79-111` 生成的 `onManifestLoaded` 把整个 `for` 放在一层 `try/catch` 内。若某一行在 `Loader` 构造、事件注册、URL 解析或 `load()` 调用时同步抛错，控制流直接跳到外层 `catch`，后面的清单行全部不再执行，并统一记作 `err_loader`。README `:134` 的“任何失败只记标记，绝不阻断游戏”只对游戏主循环而言；它不保证其他模组继续加载。当前清单无已知能触发此路径的错误行；这是故障隔离不足。建议逐行校验并逐行 `try/catch`，记录行号和入口名，继续处理后续行。

### P2：可编辑清单的格式错误多数被静默忽略

`patch_game_swfs.ps1:92-103` 只按 `|` 切列，删除 CR，不对目录名、入口名、开关做 `trim`，不校验列数恰为 5，也不报告不合格行。比如把 `1` 写成 `1 `、行前加空格、列数不足，行会被跳过或拼出错误路径；列数不足时根本不会产生 README `:158` 所暗示的 `err_<入口类>`。当前清单字节无 BOM、七行均五列、开关有效；风险来自日常手工编辑。建议明确逐行错误和行号，限制目录/类名为单个合法路径段，发现错误时给出可靠状态，而不是无声跳过。

### P2：清单行序只决定请求发起顺序，不能保证 `init` 顺序

`patch_game_swfs.ps1:93-104` 连续调用多个 `Loader.load()`，真正的 `init(this)` 在各自异步 `Event.COMPLETE` 回调（`:121-137`）里执行，没有等待前一模块完成。README `:83` 正确称“加载发起顺序”，但 `:92` 的“调整加载顺序”容易被理解为能建立模块依赖次序。现有旧 loader 也同样异步，这不是已观察到的当前回归；新模块若依赖前一模块已初始化，单纯移动清单行不可靠。建议在使用手册写明边界；若确实需要依赖顺序，增加串行队列或显式依赖机制。

## 较小的文档偏差

- README `:81` 称 `init` 必须是 `public static function init(main:*)`，实际 Sandevistan 和 RConnect 源码使用 `main:Object`，且 MainFE 实例可作为 Object 传入。真正的契约是可从入口类静态调用、能接收 MainFE 实例；通配符 `*` 不是必需。
- README `:104` 称每步自校验、“原子替换”，但上述调用集合和三目标整体一致性没有被验证。当前替换是每个文件分别备份、复制、移动，不能据此推断三目标作为一组原子提交。
- README `:211-213` 已指出根 `AGENTS.md` 的六模组矩阵和部分技能过时；本次未改受保护的治理文件。
